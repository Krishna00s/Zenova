\# Platform Architecture



\## Purpose



Zenova is no longer just a marketing website.



It is a platform that helps us showcase our work, manage projects, collaborate with clients and grow the agency over time.



The public website tells our story.



The private platform helps us run the business.



Visitors should never notice where one ends and the other begins.



Everything should feel like one connected ecosystem.



\---



\# Platform Structure



The platform consists of two major parts.



\## Public Experience



Accessible to everyone.



This includes:



\- Homepage

\- About

\- Services

\- Dedicated Service Pages

\- Contact



The purpose of the public experience is to introduce Zenova, showcase our work and help potential clients understand how we work.



\---



\## Private Platform



Accessible only to authenticated users.



This includes:



\- Dashboard

\- Client Portal

\- Content Management

\- Media Library

\- User Management



The private platform exists to manage the company without modifying the website's source code.



\---



\# Dedicated Service Pages



Every service shown on the homepage should have its own dedicated page.



Examples:



/services/web-development



/services/video-editing



/services/ad-creation



/services/paid-promotions



These pages should keep the same visual identity as the homepage while focusing entirely on one service.



Each page should contain:



\- Hero Section

\- Service Overview

\- Previous Work

\- Case Studies

\- Technologies or Tools

\- Process

\- Frequently Asked Questions

\- Contact Section



These pages should feel like a continuation of the homepage rather than separate websites.



\---



\# Dynamic Content



Projects should never be hardcoded into React components.



Everything should come from the backend.



Examples include:



\- Projects

\- Case Studies

\- Testimonials

\- Team Members

\- Hero Content

\- Blogs

\- Service Information



The frontend should only display the data it receives.



\---



\# Dashboard



The Dashboard is the control center for Zenova.



Team members should be able to manage the platform without editing source code.



Examples of dashboard features:



\- Create Projects

\- Edit Projects

\- Upload Images

\- Upload Videos

\- Manage Testimonials

\- Publish Blogs

\- Manage Team Members

\- Update Service Pages

\- View Contact Requests



Publishing new content should automatically update the public website.



\---



\# Client Portal



Clients should have their own secure workspace.



Each client should only see information related to their own projects.



The client portal may include:



\- Project Progress

\- Timeline

\- Deliverables

\- Shared Files

\- Messages

\- Downloads



The portal should feel clean, calm and easy to understand.



\---



\# Authentication



The platform should support secure authentication.



Different users should have different permissions.



User Roles:



Visitor



Client



Team Member



Administrator



Each role should only access the parts of the platform that belong to them.



\---



\# Media Library



Images, videos and documents should be managed from a central media library.



Media should not be manually added into the project's source code.



Supported content includes:



\- Images

\- Videos

\- PDFs

\- Client Logos

\- Brand Assets

\- Documents



\---



\# Security



The platform should follow modern security practices.



This includes:



\- Secure Authentication

\- Role Based Access Control

\- Password Encryption

\- Protected Routes

\- Input Validation

\- Secure File Uploads

\- Session Management

\- Rate Limiting

\- Audit Logs



Security should be considered from the beginning rather than added later.



\---



\# Scalability



The platform should be designed for long-term growth.



Future features should be possible without rebuilding the existing architecture.



Possible future additions include:



\- Blog

\- Careers

\- Knowledge Base

\- CRM

\- Proposal Generator

\- Invoicing

\- Contracts

\- Analytics

\- Internal Notes

\- Team Calendar



The architecture should support these additions naturally.



\---



\# Design Consistency



Every page inside the platform should follow the same design language.



This includes:



\- Typography

\- Colors

\- Motion

\- Spacing

\- Components

\- Navigation

\- Footer



Whether someone is on the homepage, a service page, the dashboard or the client portal, the experience should always feel unmistakably like Zenova.



\---



\# Visual References



Design references are an important part of the development process.



Each major page should have its own visual reference before implementation.



Examples include:



\- Homepage

\- Web Development

\- Video Editing

\- Ad Creation

\- Paid Promotions

\- About

\- Contact

\- Login

\- Dashboard

\- Client Portal

\- Project Details

\- Case Study



These references are not meant to be copied.



They exist to communicate atmosphere, storytelling, layout and interaction design before development begins.



\---



\# Technology



The platform should be built using reliable technologies that have generous free tiers during the early stages.



The architecture should avoid unnecessary vendor lock-in and allow migration to paid infrastructure in the future without major rewrites.



Technology choices should prioritize:



\- Stability

\- Security

\- Maintainability

\- Scalability

\- Developer Experience



rather than following trends.
